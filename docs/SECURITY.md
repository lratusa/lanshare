# LanShare v2 安全说明

一句话：**同一 WiFi 下抓包的人看不到你传了什么；密钥不经过网络。** 这不是“绝对安全”，下文的“不防什么”一节同样重要。

## 防谁、防到什么程度

| 对手 | 能做什么 | v2 的结果 | 怎么验证的 |
|---|---|---|---|
| 同一 WiFi 下**被动抓包**的人 | 记录所有经过的网络流量 | 看不到文件内容、文件名、文字消息、二维码密钥、口令、会话密钥；也无法冒用别人的会话 | 抓包测试（见下文“验证”） |
| 知道地址、没有二维码也没有口令的人 | 直接访问 `http://电脑IP:端口` | 只能拿到公开的页面和脚本；所有数据接口 401/403 | 服务端攻击用例测试 |
| 在线猜口令 | 反复尝试 6 位口令（每次只能验证一个） | 每个 IP 60 秒内 5 次、全局 60 秒内 20 次；累计 30 次没完成的尝试后**暂停口令登录**，只能在电脑上的主界面里重新开启（同时换新口令）。每开启一次，被猜中的概率不超过 30 / 1,000,000 | 暂停与恢复测试 |
| 抓包后**离线**暴力破解口令 | 拿着抓到的握手数据在自己电脑上穷举 | 做不到：口令登录用 SPAKE2，抓到的消息无法用来验证猜测 | 协议性质（见“协议摘要”） |
| 重放抓到的请求 | 把录下的密文原样再发一遍 | 拒绝（403）；把 A 接口的密文挪到 B 接口也拒绝 | 重放、跨接口重放测试 |
| 恶意网页（DNS rebinding） | 让你的浏览器以自己的域名访问 LanShare | Host 头不是 IP 字面量或 `localhost` 一律 421 | Host 校验测试 |
| 恶意网页（跨站请求） | 借你的浏览器往 `127.0.0.1:8000` 发口令尝试、刷掉限额 | 握手接口只收 `application/json`（浏览器跨站发送必须先预检，而服务端不回应预检）；带外站 `Origin` 的请求一律 403 | 跨站请求测试 |
| 局域网里耗资源 | 大量连接、只发一半的请求、不传完的上传、超大的上传 | 先验请求头再读正文；连接、正文、上传都有数量上限和超时，并且按来源 IP 分开计数（见“实现层面”）；内存占用有上界 | 资源上限测试 |
| 恶意文件名 | 上传名为 `..\..\x`、`CON`、含 Unicode 双向控制符的文件 | 清理后落在共享文件夹内，显示不被伪装 | 文件名清理测试 |
| 局域网里其他设备 | 调用“在资源管理器中显示”等本机操作 | 只接受来自本机回环地址的请求 | 非本机调用测试 |
| 拿到二维码或口令、在**别的设备**上连接的人 | 二维码被拍照、截图，或者留在扫码 App 的历史里；口令被人看见或猜中 | 握手能成功，但连文件列表都看不到：局域网里第一次连上来的设备，要电脑前的人在主界面上核对 4 位验证码、点“允许”才放行（按 IP 记，这次运行内有效） | 新设备确认测试（`tests/approval.rs`） |

## 不防什么（诚实边界）

1. **主动中间人**。页面本身通过 HTTP 下发。如果有人在同一网络里主动攻击（ARP 欺骗、搭恶意热点），可以篡改手机**首次加载**的页面脚本，从而拿到密钥。这是“手机不装 App、只用浏览器”这一类工具的共同上限；自签名 HTTPS 也挡不住，还会让浏览器弹出吓人的警告。v2 防的是**窃听**，不是主动篡改。
2. **流量特征**。传了多大的文件、什么时候传，抓包的人仍然看得到（密文长度≈明文长度）。
3. **二维码泄露，挡住的是“直接连上来”，挡不住“抓包解密”**。二维码里就带着密钥 K；放行过的设备（包括用口令配对的）会经加密信道拿到 K，以便下次打开页面直接连接。新设备要在电脑上点“允许”，所以光拿到二维码连不上来。但还要知道：
   - 持有 K 的人如果同时在同一 WiFi 里**抓包**，就能解密**已经放行的设备**的流量（会话密钥由 K 和明文的会话号派生，同一次运行内没有前向保密）。他想用那个会话发请求，门看的是请求来源的 IP，还得同时冒用那台设备的 IP。要挡住这一条，得在握手里加一次性的密钥交换，v2 没有做；
   - 放行是按 IP 记的：和放行过的设备共用一个 IP 的设备（比如都在同一个路由器的 NAT 后面）会一起被放行；冒用别人的 IP 属于主动攻击（见第 1 条）；
   - 持有 K 或口令的人可以反复连接捣乱：占满 8 个待确认名额（正常设备会收到“等的设备太多”），每 30 秒让主界面弹出一次；反复扫码握手开新会话，会把别的设备的会话挤掉（它们会自动重连）。会打扰，不会泄密（属于第 6 条）。开新会话的次数有上限（见“实现层面”），所以也耗不光内存；
   - 电脑前的人点错了“允许”，或者想让所有扫过码、输过口令的设备立即失效：从托盘退出程序再打开。新的一次运行会换新的 K 和口令，放行记录也全部清空。
4. **本机上的其他程序**。密钥在本机这几处可读：`%LOCALAPPDATA%\LanShare\instance.json`（单实例记录）、主界面窗口的启动命令行、浏览器对该地址的 localStorage。同一 Windows 用户下运行的恶意软件不在防护范围内。
5. **落盘不加密**。文件收到后以原样保存在共享文件夹（默认“下载\LanShare”），加密只保护**传输过程**。
6. **局域网内的拒绝服务**。同一网络里的人可以让服务变慢或连不上：比如用很多个 IP 占满连接名额，或者持续发起口令登录让口令登录暂停。v2 保证的是**不会因此泄密、不会把内存或磁盘耗尽**，本机界面有单独的连接名额，扫码路径不受口令暂停影响；但不保证在有人捣乱时其他设备一定连得上。（在局域网里捣乱本来也可以直接干扰 WiFi。）

7. **二维码网址可能留在别处**。扫码 App 或手机浏览器可能记住了带 `#密钥` 的网址（甚至随云同步上传）。页面会立刻把它从地址栏抹掉，但管不到别的 App 的历史记录。这个密钥只在本次运行有效。

每次启动，程序都会重新生成密钥和口令：电脑上的程序一重启，旧二维码、旧口令全部失效。

## 协议摘要

完整设计见 `docs/superpowers/specs/2026-10-02-lanshare-v2-rust-design.md` 第 3、4 节。

**密钥分发：二维码 + URL 片段。** 二维码内容是 `http://IP:端口/#<32 字节密钥 K 的 base64url>`。按浏览器规范，`#` 后面的片段**不会出现在任何 HTTP 请求里**，所以密钥不经过网络。页面一打开就用 `history.replaceState` 把它从地址栏抹掉（先抹掉，再加载加密模块）。

**扫码握手。** 浏览器生成随机会话号 `cid`，发送 `HMAC(HKDF(K, "lanshare/2 hello"), "hello" ‖ cid)` 证明自己持有 K。双方各自算出 `session_secret = HKDF(K, salt=cid, "lanshare/2 session")`，再派生出两个方向各一把密钥。密钥本身从不出现在网络上。

**口令登录：SPAKE2**（Ed25519 群，身份绑定 `"lanshare/2|" ‖ server_id`），双方再互发确认标签。窃听者拿到全部消息也无法离线验证口令猜测；主动攻击者每次只能试一个口令，并受限速约束；累计 30 次没完成的尝试后口令登录暂停，只能在本机主界面重新开启（见下文 I-1）。

**加密信道。** 登录后的所有请求都是 POST，请求体和响应体都是 **ChaCha20-Poly1305** 密文：

- nonce = 4 个零字节 ‖ 64 位计数器（大端），每个请求计数器 +1；两个方向用不同密钥，所以每个 (密钥, nonce) 只用一次；
- 附加数据（aad）绑定接口路径，密文挪到别的接口会解密失败；
- 服务端用 4096 宽的滑动窗口防重放，**解密成功后**才登记计数器（伪造的密文不会占用计数器）；
- 会话最多 256 个，被淘汰的会话号本次运行内永不再接受（防止重放旧握手“复活”会话、计数器归零）；
- 明文的 HTTP 请求里只有：会话号、计数器、密文长度、接口路径（上传/下载的路径里是随机 id，不是文件名）。

**浏览器里的密码学代码**由同一份 Rust 代码编译成 WebAssembly（约 94 KiB），不依赖 `crypto.subtle`：手机通过 `http://局域网IP` 访问时不是浏览器的“安全上下文”，`crypto.subtle` 根本不可用。

## 实现层面

- **语言**：服务端和浏览器端的加密代码都是 Rust。`unsafe` 只出现在两处：WASM 与 JavaScript 的边界、调用 Windows API 的地方，每处都写了 `// SAFETY:` 说明。
- **密码学库**：RustCrypto 的 `chacha20poly1305` 0.10.1、`hkdf` 0.12.4、`hmac` 0.12.1、`sha2` 0.10，以及 `spake2` 0.4.0。不自己实现任何密码学原语。其中 `chacha20poly1305` 经过 NCC Group 的独立安全审计（见其 README）；`spake2` 0.4.0 的说明里写明它从未经过独立第三方审计，口令登录依赖它。
- **常量时间比较**：HMAC 校验用库自带的 `verify_slice`。
- **日志**：不写入密钥、口令、会话密钥、文件内容（有测试检查）。
- **网页**：不使用 `innerHTML` 等 HTML 注入点（测试强制）；响应头带 CSP：`default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; ...; frame-ancestors 'none'`，外加 `X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store`。
- **请求大小与先后顺序**：握手 4 KiB；RPC 明文 64 KiB；每块 1 MiB。加密接口先只看请求头（类型、声明的长度、会话是否存在、计数器是否在窗口内），全部合格才开始读正文。
- **资源上限**：
  - 连接：每个来源 IP 最多 16 个；局域网来的合计最多 256 个，本机回环单独 32 个（局域网占满了，本机界面照样能用）；超过上限的连接立即关闭；
  - 时限：请求头 10 秒内必须收完（这也意味着空闲的 keep-alive 连接 10 秒后关闭，浏览器会自动重连）；握手接口的正文 10 秒内必须收完；任何方向 60 秒没有收发就断开；
  - 正文：同时最多 32 个在读，每个来源 IP 最多 8 个；排队最多 30 秒；一块（1 MiB）5 分钟内要收完（约 3.5 KB/s，很慢的网络也够用）；
  - 新会话：扫码握手成功、开新会话，每个来源 IP 每 60 秒最多 30 个，全局最多 300 个（同一个会话号再握手不算），超过回 429，不建会话、也不挤掉已有的会话。会话表满时每开一个就挤掉最久没用的一个，被挤掉的会话号要在这次运行内一直记着（防止重放旧握手“复活”会话），这个上限让这份记录最多每分钟多 300 条；口令登录另有更严的限速；
  - 上传：未完成的全局最多 64 个、每个会话最多 4 个，10 分钟没有新块就作废并删除临时文件（只查进度不算有动静）；单个文件最大 1 TiB；预占空间后磁盘至少还要剩 512 MiB（检查和预占串行进行）。
- **落盘不覆盖**：收到的文件改名时用不覆盖的方式（Windows 上 `MoveFileExW` 不带替换标志），同名文件永远不会被悄悄覆盖。
- **端口**：Windows 上用 `SO_EXCLUSIVEADDRUSE` 独占绑定，别的程序不能和它共用端口、截走发往 `127.0.0.1` 的请求。

## 独立安全审查

2026-10-02，由一个没有参与开发的独立审查者（这不等于专业的人工安全审计）做对抗性审查：通读设计和代码，每条发现都写 PoC 实测。结论：**没有 Critical**；协议核心（加密、nonce 唯一、防重放、防会话复活、路径穿越、XSS/CSP）经读代码和实测都成立。发现的问题和处理：

| 编号 | 问题 | 处理 |
|---|---|---|
| I-1 | 口令可以被长期在线猜测：只有每分钟 20 次的限速，没有总量上限，30 天约 58% 的概率猜中；“失败 10 次换口令”不降低攻击者的成功率 | 累计 30 次没完成的尝试后暂停口令登录，只能在本机主界面重新开启（同时换新口令）；去掉自动换口令 |
| I-2 | 没传完的上传永不过期，64 个名额会被正常使用耗尽；并发检查有竞态；预占磁盘不留余量 | 上传 10 分钟没有新块就作废并删临时文件（后台定时清理）；全局和每会话名额在同一次加锁里检查并占位；预占后至少留 512 MiB；单文件 1 TiB 上限 |
| I-3 | 不需要密钥就能让服务端把 1 MiB 请求体整块收进内存，连接不设上限、不超时（实测 300 个连接占 526 MiB） | 先验请求头再读正文；正文读取限量、限时；连接数上限 + 空闲 60 秒断开 |
| M-1 | 卸载脚本只靠“目录名叫 LanShare”防误删，和默认共享文件夹同名，可能递归删掉用户文件 | 安装目录以注册表登记的位置为准；只删安装时放进去的 3 个文件，目录空了才删 |
| M-2 | 握手接口接受 `text/plain`，任何网页都能跨站发口令尝试 | 握手接口只收 JSON；带外站 `Origin` 的请求一律拒绝 |
| M-3 | Rust 的 `fs::rename` 在 Windows 上会覆盖已存在的文件，并发时同名文件可能被悄悄覆盖 | 改用不覆盖的改名，并去掉“先查 exists() 再改名”的竞态 |
| M-4 | 密钥 K 无法撤销 | 写进上文“不防什么”：退出再打开即全部失效；说明持有 K 加录包的后果 |
| M-5 | 文档与实现不一致（Host 校验）、块编号乘法可能溢出、密钥在地址栏多停留了加载 WASM 的时间 | 文档改正；`checked_mul`；先抹地址栏再加载 |

每条修复都有回归测试（`crates/lanshare/tests/hardening.rs`，卸载脚本有沙箱测试），并做了变异测试：把修复故意改回去，对应测试必须失败。

**复验**：同一位审查者用原来的 PoC 对修复后的代码再跑一遍。上面 7 条全部关闭（I-2、M-1、M-2、M-3 有实测输出）。复验同时指出，第一版修复本身带来了新问题：

| 编号 | 问题 | 处理 |
|---|---|---|
| N-1 | 新加的连接上限是全局的、不分来源，局域网一台机器就能占满，连本机界面都进不来；读请求头仍没有绝对时限 | 不再用 axum 自带的 `serve`，自己接收连接交给 hyper 并配上计时器：请求头 10 秒时限；每 IP 连接上限；本机回环单独一池；超限立即关闭 |
| N-2 | 读正文的名额是全局的，知道一个明文会话号就能占用 | 每个来源 IP 最多 8 个 |
| N-3 | 一整块必须 60 秒内收完，很慢的网络永远传不完 | 放宽到 5 分钟（空闲由连接层的 60 秒计时管） |
| N-4 | 暂停前的并发请求可以超过上限（30 实际能到约 49）；完成配对的接口不检查暂停 | 暂停检查、限速、计数在同一次加锁里完成，先占位再计算；完成接口也检查暂停 |
| N-5 | 剩余空间检查不在锁里；只查进度就能让上传一直不过期 | 检查与预占串行；查进度不再刷新活动时间 |

这些也都有回归测试和变异测试。

**第三轮复验**（专门看新的连接层）：N-1 ~ N-5 全部关闭，没有新的 Important。新发现 3 个 Minor：

| 编号 | 问题 | 处理 |
|---|---|---|
| R3-1 | 握手接口（hello、PAKE）读正文没有时限，一个连接每隔 25 秒发一个字节，100 秒后还挂着（实测） | 限量（4 KiB）、限时（10 秒）读正文 |
| R3-2 | 请求头时限同时起到“空闲 keep-alive 10 秒关闭”的作用，客户端恰好在第 10 秒复用连接时请求会被切断 | 写进文档；浏览器遇到复用的连接被关会自动重发 |
| R3-3 | 接收连接出错时一律等 50 毫秒，对方反复建立又重置连接可能拖慢接收 | 连接级错误立即继续，其它错误才等待，等待时也响应退出 |

**新设备确认**（2026-10-03 加的，见 `docs/superpowers/specs/2026-10-03-device-approval.md`）是在上面三轮审查**之后**才加的，没有经过独立审查；它有自己的单元测试、集成测试，并用真实的 exe 和两个浏览器走过允许、拒绝两条路。

另记一条说明：程序只监听 IPv4。将来如果改成同时监听 IPv6，按 IP 计数和判断本机之前要先把 IPv4 映射地址规范化，IPv6 要按网段计数。
