# 第 11 章　从第一性原理看架构：六条事实，七个步骤

## 这一步要解决什么

前 10 章一行一行写出了 LanShare。这一章不写代码，回答一个问题：**这些设计是从哪儿来的？**

很多人学架构，是在背清单：要分层、要加缓存、要用消息队列。清单回答不了“为什么”。不知道为什么，换一个场景就不知道该不该用。

这一章换一种学法：**第一性原理**。

- **类比**：大家都这么做，所以我也这么做。比如“网页要安全，就上 HTTPS”。可在局域网里，IP 地址申请不到正规证书；自签名证书会让浏览器弹出吓人的警告，照样挡不住主动中间人。
- **第一性原理**：先找出推不翻的事实，就是在你的场景里不管怎么选都改变不了的限制（物理的、经济的、人的，也包括平台的规则），再只从它们出发，一步一步推出设计。

LanShare 里的第一个例子在第 1 章：

1. **事实**：手机用 `http://局域网IP` 打开页面不算安全上下文，浏览器根本不提供 `crypto.subtle`；何况它本来也没有我们要的 ChaCha20-Poly1305 和 SPAKE2。
2. **目标**：手机只用浏览器，不装 App。
3. 两条一合，只剩一条路：**自己带一份加密代码进浏览器**。
4. 为什么是 Rust 编成的 WASM，而不是一个 JS 加密库？还要加上后面的事实四：规则只该写一遍，两端共用同一份。

每一步都能追到一条事实或者一个目标。下面用六条事实，把主要的设计重新推一遍。

## 事实一：网络是公共的

同一个 WiFi 里的人，看得见你发的东西，也发得出假的请求。

| 推论 | LanShare 里 |
|---|---|
| 内容在离开设备之前就加密 | 端到端加密；密钥放在二维码网址的 `#` 后面，浏览器不会把它发到网络上。窃听者录下的文件和文字都是密文，看得见的只有会话号、计数器、长度这类信息 |
| 画出信任边界，每道边界都有人看门 | 网络（Host 必须是 IP 字面量或 `localhost`，拒绝外站 Origin）→ 密钥（握手）→ 设备（新设备确认）；另有一类操作只认本机，非本机调用回 `only_local` |
| 看门的地方要少、要集中 | 所有加密请求（RPC、上传、下载）都从 `channel.rs` 的 `sealed` 这一个入口进来。也照实说：“只认本机”的检查分散在 `rpc.rs` 的 5 个函数里，各查各的，靠非本机调用的测试守着；这样的操作再多几个，就该挪到分发处统一检查 |

## 事实二：资源有限，而攻击几乎不要钱

发一个请求不花钱，处理一个请求要花内存、时间和磁盘。这笔账没法让对方多花钱，但能让你少花。

**推论一：便宜的检查放前面，贵的放后面**，让每个假请求在你这里只花最少的成本。一个请求在 LanShare 里要过的关：

1. 接收连接时的准入：每个 IP 最多 16 个连接，多的当场关掉（第 9 章）；
2. 请求头 10 秒内收完；
3. 预检，只看请求头：长度、会话是否存在、计数器是否在窗口内，不读正文；
4. 每个 IP 的正文名额、全局正文名额；
5. 限时读正文；
6. 解密；
7. 新设备确认的门；
8. 真正的业务。

注意第 7 步：新设备的门很便宜，却排在昂贵的解密后面。因为只有证明了持有密钥的请求，才有资格让电脑弹窗、登记成待确认。这是事实一压过了事实二：**推论之间会打架，安全边界优先。**

**推论二：会增长的，要有上限；会等待的，要有时限。** 主要的几项：

| 东西 | 上限 | 时限 |
|---|---|---|
| 连接 | 全部 256，每个 IP 16，本机另有 32 | 空闲 60 秒断开 |
| 握手请求 | 正文最多 4 KiB | 10 秒内收完 |
| 加密请求的正文 | 同时 32 个，每个 IP 8 个 | 5 分钟内读完 |
| 会话 | 256 个，满了淘汰最久没用的 | 没有空闲时限；程序重启全部作废 |
| 新开会话（扫码握手成功） | 每个 IP 每分钟 30 个；全局 300 个 | 按 60 秒计数 |
| 上传 | 同时 64 个，每个会话 4 个 | 10 分钟没有新块就作废 |
| 口令尝试 | 每个 IP 每分钟 5 次，全局 20 次，累计 30 次暂停 | 按 60 秒计数；暂停不会自动解除，只能在电脑上重新开启 |
| 待确认的设备 | 8 台 | 60 秒没再问就撤掉 |

要有上限，是被真实的问题逼出来的：安全审查里最重的问题之一（I-3），就是一个不需要密钥的人用 300 个连接占了 526 MiB 内存。具体的值，有的实测，有的按最慢的正常情况算（正文给 5 分钟，是让每秒三四 KB 的慢网络也能传完 1 MiB 的一块），都放在 `Config` 里，测试里可以调。

也要说清楚：这些上限保证的是内存和磁盘不被耗尽，**不保证**有人捣乱时别的设备一定连得上（`SECURITY.md` 第 6 条）。

## 事实三：很多事会同时发生

两个请求可能在同一个瞬间到达，看到的是同一份状态。

**推论一：先查后改，中间不能有缝。** 第 5 章说过，检票员要等拆开信、确认是真的，才把票号记下来，不然捣蛋鬼用伪造的密文就能把票号占光。所以预检只看不记，解密在锁外做。并发的那一半在 `open_body`：解密成功以后，在同一次加锁里再查一次、马上登记：

```rust
let mut sessions = st.sessions.lock().expect("锁不会中毒");
let Some(session) = sessions.get(&cid) else {
    return Err(StatusCode::UNAUTHORIZED);
};
if !session.window.check(ctr) {
    return Err(StatusCode::FORBIDDEN);
}
session.window.commit(ctr);
```

同一个请求同时发两遍，两个都能通过预检、都能解密，到了这里只有一个能通过。同样的写法还有：口令尝试先在一把锁里计数占位，再做费时的 SPAKE2 计算（复验 N-4）；上传名额查完马上占住（审查 I-2）。

**推论二：锁里只算，慢事出了锁再做。** 新设备确认在锁里只算出“要不要弹窗”，出了锁才去启动 Edge（第 10 章）。例外：查剩余空间和预占磁盘本身就是磁盘操作，挪不出锁外（复验 N-5），那就用一把只管这件事的锁 `alloc_lock`，别让它挡住别人。

## 事实四：外部世界不确定，规则是确定的

时间、随机数、网络、操作系统、界面，又难测又常变；协议的规则，给定输入就有确定的输出。

**推论一：核心要纯，外壳要薄。** `lanshare-proto` 里没有一行网络、文件、时钟的代码，随机数由调用方传进来（服务端给操作系统的随机源，浏览器里由 JS 的 `crypto.getRandomValues` 给）。正因为纯，同一份代码能编进 exe，也能编成 WASM。往外一层也一样：新设备确认的 `now` 由调用方传入；服务端只认 `Desktop` 这个 trait（`open_app` 这个方法是第 10 章加的），真正调 Windows 的是外壳，测试里换成只记账的 `FakeDesktop`。

**推论二：同一件事只有一个真相。** 加密只写一遍，两端共用；“同一份”也可能一起错，所以已知向量用 Node 自带的 OpenSSL 这套独立实现生成。也有做不到只写一遍的地方：握手的步骤，服务端在 `auth.rs` 里用 Rust、浏览器在 `proto.js` 里用 JS 各写了一遍，所以改协议要同时改几处，再靠互通测试让真实的 exe 和真实的 JS 对着跑；网页编进 exe 以后，测试还比对 exe 里的文件和仓库里的文件的 SHA-256。同一件事写两遍，迟早两个样；非写两遍不可，就得有测试盯着。

推出来的结构，越往中间越纯、越稳定，越往外越具体、越常变：

- **协议核心** `lanshare-proto`：纯，不碰网络、文件、时钟
  - 编成 WASM → **协议客户端**（`proto.js` + WASM）→ 被 **网页界面**（`app.js`，只管界面）调用
  - 同一份代码编进 → **服务端**（边界、上限、门）
    - **桌面外壳**（托盘、窗口、资源管理器）实现服务端定义的 `Desktop` trait
- **测试**：已知向量钉住核心，攻击用例钉住服务端，互通测试钉住两边的握手

这个结构不是先画出来的，是推出来的。

## 事实五：人会犯错，包括你自己

你自己写的测试，只覆盖你自己想到的情况。

| 推论 | LanShare 里 |
|---|---|
| 用独立的东西来核对 | 另一套实现生成的已知向量；加餐之前的项目，还请了没有参与开发的独立审查者，只拿设计文档和代码，每条发现都写攻击代码实测（这不等于专业的人工安全审计）。新设备确认是审查之后加的，没有经过审查 |
| 证明测试真的会响 | 审查找到的每一条修复都做过变异测试：故意改回去，对应的测试必须变红（第 9 章） |
| 改动要小，旧测试原样通过 | 新设备确认一行旧代码都没改，旧测试原样通过；新开关在正式运行时默认打开，另有测试守着默认值 |

最后一行要补一句：新设备确认“只加不改”，有一半是课程的原因（视频课前面几集写出的代码不能动，见设计文档）。平时不必死守，长期只加不改代码会越积越乱；要守的是改动小、好验证。

## 事实六：最后做判断的是人

用户要知道能信什么、不能信什么；有些决定只有人能做。

- **照实写出边界**：`SECURITY.md` 专门一节“不防什么”。宣传只说“同一 WiFi 下抓包的人看不到你传了什么”，不说“绝对安全”。
- **把关键决定交给人，并且给人核对的依据**：哪台设备是自己的，只有电脑前的人知道，所以新设备要电脑前的人点头，还有 4 位验证码可核对；口令登录被暂停后，只能在电脑上重新开启。

## 每个决定都有代价

| 决定 | 换来的 | 付出的 |
|---|---|---|
| 不用 wasm-bindgen | 依赖少，没有工具版本要对齐 | 自己管线性内存和裸指针 |
| 不用 `axum::serve` | 请求头有时限，每个 IP 单独限额 | 自己写接收连接的循环 |
| 只用浏览器、不装 App | 手机扫码就能用 | 页面每次从网络加载，挡不住主动中间人 |
| 密钥只活一次运行 | 重启就能让所有设备失效 | 每次重启都要重新扫码 |
| 新设备按 IP 放行 | 协议不用改，刷新页面不用再点 | 共用一个 IP 的设备会一起放行 |

第一性原理不会给你完美的答案，它给你的是：每个决定从哪来、换来了什么、付出了什么。代价写下来，以后情况变了，就知道该回头改哪一条。

## 以后设计你自己的系统：七个步骤

每一步都写下一样具体的东西：

1. **目标和非目标**：为谁、解决什么问题；明确不解决什么。
2. **事实清单**：网络、资源、并发、外部世界的不确定、人会犯错、由人判断，再加上你场景特有的限制（比如平台规则）。
3. **边界图**：谁可信、数据从哪来、每道边界由哪段代码看门，看门的地方够不够集中。
4. **威胁和故障清单**：什么都没有的人能做什么？拿到密钥或口令的人能做什么？什么会无限增长、什么会无限等待？最便宜的攻击是什么？
5. **决定和代价表**：每个决定追到哪条事实、换来什么、付出什么；推论打架时写下谁让谁。追不到事实的，多半是照搬。
6. **测试清单**：每个决定由哪个测试守着；把修复故意改回去，测试必须变红；用到的数字要么实测，要么写清楚怎么算的。
7. **“不防什么”和演进余地**：照实写出边界，交给用户判断；核心纯、外壳薄；改动小、旧测试原样通过；新功能有开关，默认落在安全的一边。

## 和 Python 对照

| 推论 | Python 项目里 |
|---|---|
| 看门的地方集中 | 中间件最集中；装饰器省了重复代码，但每个视图还得记得挂上 |
| 便宜的检查在前 | 先看请求头里的 `Content-Length` 再读正文；先查权限再查数据库 |
| 有上限和时限 | `requests.get(url, timeout=10)`（requests 默认不设超时，忘写是很常见的疏忽）；`queue.Queue(maxsize=...)`；小心 `functools.cache` 和 `lru_cache(maxsize=None)`，它们没有上限（`lru_cache` 默认上限 128） |
| 先查后改不留缝 | 查和改放进同一个 `with lock:`，但 `threading.Lock` 只管得住同一个进程里的线程；多进程、多台机器靠数据库：唯一约束、`INSERT ... ON CONFLICT`，或者事务里加行锁。默认隔离级别下，光开一个事务挡不住“先 `SELECT` 再 `INSERT`” |
| 核心纯、外壳薄 | 计算写成纯函数，`now`、随机数、读到的内容当参数传进去，测试不用 `mock.patch` |
| 一件事只有一个真相 | 前后端共用的规则只写一份；用标准文档里的测试向量核对，不拿自己的输出和自己比 |
| 默认安全 | 新功能用开关接上，默认值选安全的一边 |

## 小测验

**1. “大公司都用这个框架，所以我们也用”和“局域网地址下浏览器不给加密接口，而手机只用浏览器，所以得自己带加密代码”，哪个是第一性原理的理由？**

<details><summary>答案</summary>

后者。它从一条推不翻的事实（局域网地址不是安全上下文，浏览器不提供 `crypto.subtle`）加上一个明确的目标（手机只用浏览器）出发，只剩一条路。前者是类比，大公司的场景和限制可能和你完全不同。
</details>

**2. 从“攻击几乎不要钱，处理请求要花内存”能推出什么？为什么“换一台内存更大的电脑”不是答案？**

<details><summary>答案</summary>

越便宜的检查越靠前，能早拒绝就早拒绝，再给会增长的东西设上限。换大内存不解决问题：内存再大也有限，攻击者的成本却几乎为零，这笔账永远算不过来。
</details>

**3. 两个一模一样的重放请求同时到达，下面的写法有什么问题？**
```rust
let ok = st.sessions.lock().unwrap().get(&cid).unwrap().window.check(ctr);
if ok {
    st.sessions.lock().unwrap().get(&cid).unwrap().window.commit(ctr);
}
```

<details><summary>答案</summary>

检查和登记分在两次加锁里，中间有缝：两个请求可能都在登记之前查到“没用过”，都通过。注意 Rust 的细节：`lock()` 拿到的锁（`MutexGuard`）在这一行结束时就被丢弃、锁随即放开，这和 Python 的 `with` 块不同，不会一直拿到块结束。要在同一次加锁里，用同一个 guard 先查后登记。
</details>

**4. 为什么协议核心连随机数都不自己取，而是让调用方传进来？**

<details><summary>答案</summary>

随机数的来源在不同环境里不一样：服务端用操作系统的随机源，浏览器里的 WASM 拿不到操作系统随机源，只能由 JS 的 `crypto.getRandomValues` 提供。核心不碰这些，才能同一份代码两边编译；测试时也能传入固定的输入。
</details>

**5. 挑一个你写过的项目，写下它推不翻的三条事实。现在的设计能从这三条事实推出来吗？**

<details><summary>答案</summary>

没有标准答案。常见的发现：有些设计追不到任何一条事实，是当初照搬的，可以重新考虑；有些事实没有被任何设计照顾到，比如某个会无限增长的列表没有上限、某个外部请求没有超时，那就是最该先改的地方。
</details>
